Add migration 14, the Phase 8 snapshot schema (B-104)

What: one migration, Migration(14, "snapshots_v1", _m14_snapshots_v1),
built from B-104-DDL v4.1 section 3 (v4 signed off by Rama 23 Nov, the
v4.1 items 24 Nov). In order: tables keys, key_challenges,
admin_approvals and snapshots (each with its indexes); columns
reservations.save_snapshot (INTEGER NOT NULL DEFAULT 0, so every
existing booking keeps PRESERVE), jobs.snapshot_id (REFERENCES snapshots
ON DELETE SET NULL) and setups.snapshot_enabled (DEFAULT 0); then the
restore job kind. The jobs.kind CHECK is rewritten in place the way
migration 6 rewrote reservations.state: a writable_schema text edit plus
a schema_version bump, never a table rebuild, so no row is touched and
no ON DELETE action can fire. Each statement is its own conn.execute()
(no executescript, which would commit apply()'s transaction).
Everything is IF NOT EXISTS or add_column, and the rewrite skips when
done, so the migration is idempotent; it creates none of the
reverted-schema guard markers. No new TEXT column accepts an S-shaped
value: each has a closed CHECK (tested on all 26), and every timestamp
carries the YYYY-MM-DDTHH:MM:SSZ shape CHECK. models.JOB_KINDS, the
engine and the API are unchanged; nothing creates a restore job yet.

v4.1 (signed off by Rama 24 Nov; each one is marked "# v4.1-N" in
migrations.py):
1. idx_admin_approvals_one_open also covers approved, not yet executed
   approvals, so a second reset for the same target can't be opened.
2. keys keeps CHECK ((state = 'pending') = (activated_by IS NULL)) and
   adds CHECK ((activated_by IS NULL) = (activated_at IS NULL)).
3. The jobs.kind rewrite skips only on the exact new kinds text,
   otherwise requires the old text exactly once, else raises; apply()
   then rolls back, leaving user_version and the schema unchanged.
4. A lost_key_reset targets key:<id>. At execution the key is revoked
   only if it is still active, and its snapshots are deleted only then.
   This migration enforces neither; the tests follow the rule, and the
   code rules are for B-105/B-106.
5. A home_discard targets setup:<name>.
6. "(inferred)" is dropped from the one-open index only.

Why: B-104 is the schema every later Phase 8 task (keys, challenges,
snapshot capture and restore, two-admin approvals) builds on. One
migration means a DB is either fully pre-snapshot or fully snapshot-
capable (Q-5). The 12/13 placeholders and the guard (PR #9) make it safe
to start at 14.

Operational note: the engine refuses to start unless the DB is at the
latest schema version (engine.py:629-633), and that is now v14. Every
existing DB therefore needs `daolab init` once after this lands, before
the engine is started.
