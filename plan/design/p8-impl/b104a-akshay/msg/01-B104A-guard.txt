Burn migrations 12 and 13 and refuse reverted Phase 8 schemas (B-104)

What: migrations 12 and 13 are registered no-ops (burned_reverted_v12,
burned_reverted_v13; errata E-4). The reverted B-104 attempt (4ec115e,
reverted in 9c8a089) used both numbers, so the B-104 migration starts at
14, and _check_contiguous needs 12 and 13 to exist. A new public
migrations.refuse_reverted_schema() raises a new
RevertedSchema(Exception) if the DB has any one of six markers that only
the reverted v12/v13 created: table user_keys; column jobs.secret; table
snapshots without public_id; column snapshots.wrapped_dek; column
setups.snapshot_bdfs; a reservations.save_snapshot whose declared
default is 1. The markers are a closed list of (fixed label, check)
pairs. The check reads only sqlite_master and PRAGMA table_info, ignores
user_version, and changes nothing. The message names only the fixed
labels: no row values, usernames, path, SQL text or version. It runs in
two places. migrations.apply() calls it on every call, right after the
SchemaTooNew check and before any migration runs; daolab init catches
RevertedSchema together with SchemaTooNew and exits 1 with the message,
with no traceback. Engine startup calls it right after the existing
version check (engine.py:629-633) and refuses the same way that check
does: "error: <message>" on stderr, exit 1, before any tick.
SchemaTooNew is not reparented and is still checked first. Migrations
1-11 are untouched.

Why: a DB migrated by the reverted code reports user_version 12 or 13.
With 12 and 13 burned, apply() would skip straight past them, and the
B-104 migration's CREATE TABLE IF NOT EXISTS / add_column would
silently keep the old shapes: a snapshots table with no public_id and
with wrapped_dek, and save_snapshot DEFAULT 1, which inverts the
PRESERVE default. The guard checks the schema rather than the version
number, because a healthy DB can stop at 12 or 13 after a crash
between two migrations, and that state must still resume. The engine
needs the guard too: with 13 now the latest version, a reverted v13 DB
passes the engine's current == latest check, so without it the engine
would start on one. A refused DB is recovered by moving it aside and
running daolab init on a fresh one. The API has no schema check; adding
one, with the guard, stays a follow-up (Q-3).

Operational note: the engine refuses to start unless the DB is at the
latest schema version (engine.py:629-633), and that is now v13. Every
existing DB therefore needs `daolab init` once after this lands, before
the engine is started. On a clean v11 DB that applies the two no-ops
and changes nothing else.
